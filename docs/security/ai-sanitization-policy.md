# AI 生成链路脱敏策略 v0.1

> 适用模块：智学导评 V0.2｜真实 AI Provider 调用与 AI 生成结果保存  
> 适用阶段：教师上传课次材料、生成知识主干、后续生成导学案/小测题/评语等 AI 功能  
> 文档性质：安全与隐私策略文档。确认后再同步到代码与测试。  
> 协作文档：`docs/prompts/knowledge-outline-generation-v0.2.md`

---

## 一、目标

本策略用于约束教师材料进入真实 AI Provider 前、以及 AI 生成内容保存前的脱敏处理。

目标不是删除所有教学信息，而是避免以下内容进入外部模型或出现在 AI 自动生成结果中：

1. 真实学校、部门、教师、班级、学生等行政或个人信息；
2. 手机号、邮箱、身份证号、详细地址等个人联系方式或身份信息；
3. API Key、账号密码、Token、密钥、内部系统地址等敏感凭据；
4. 未经确认的真实企业、真实业务数据、真实客户信息；
5. 不应由 AI 自动扩散的内部管理要求、真实制度名称或具体组织信息。

AI 功能应优先保留教学所需的知识点、课程内容、任务结构、案例类型和职业素养方向。

---

## 二、与 Prompt 文档的边界

知识主干 Prompt 文档负责定义：

- 生成什么；
- 如何判断教学重心；
- 如何处理材料依据；
- 如何输出知识主干结构；
- 如何避免思政硬贴和事实编造。

本文档负责定义：

- 哪些信息需要脱敏；
- 何时脱敏；
- 如何替换；
- 如何测试；
- 哪些内容可以保留；
- 哪些内容必须阻断或移除。

知识主干 Prompt 不负责定义具体正则、替换词和代码实现。  
脱敏策略也不负责决定知识主干的教学结构。

---

## 三、脱敏阶段

### 3.1 输入侧脱敏

教师上传的课次信息、教案、课件解析文本、课堂任务、补充材料等内容，在进入真实 AI Provider 前必须经过脱敏处理。

输入侧脱敏应覆盖：

- 课次标题；
- 课次说明；
- 材料标题；
- 材料正文；
- 从文件中解析出的文本；
- 可能被拼入 Prompt 的任何教师上传内容。

脱敏后的内容才可以进入 DeepSeek 等真实外部模型。

### 3.2 输出侧脱敏

AI Provider 返回的生成结果，在保存到数据库前应进行一次轻量脱敏兜底。

输出侧脱敏用于防止模型根据上下文重新生成具体班级名、学校名、教师名、学生姓名等敏感信息。

输出侧脱敏对象包括：

- 知识主干草稿；
- 后续导学案草稿；
- 小测题草稿；
- AI 评语草稿；
- 其他由 AI 自动生成并持久化保存的内容。

---

## 四、需要脱敏的信息类型

### 4.1 行政与组织信息

应脱敏或泛化：

- 具体学校名称；
- 具体院系、部门、教研室名称；
- 具体教师姓名；
- 具体班级名称；
- 具体学生姓名；
- 学号、工号；
- 具体校内组织或项目组名称。

建议替换为：

- `某校`
- `某部门`
- `某教师`
- `某班级`
- `某学生`
- `某项目组`

示例：

- `23物联网2班` → `某班级`
- `张老师` → `某教师`
- `沈阳某某学校` → `某校`

### 4.2 个人联系方式与身份信息

必须脱敏：

- 手机号；
- 邮箱；
- 身份证号；
- 家庭住址；
- 微信号、QQ号；
- 其他可识别个人身份的信息。

建议替换为：

- `某手机号`
- `某邮箱`
- `某身份证号`
- `某地址`
- `某联系方式`

### 4.3 凭据与系统安全信息

必须移除或替换：

- API Key；
- Token；
- 密码；
- Cookie；
- 数据库连接串；
- 内部服务器地址；
- 内网 IP；
- 账号登录信息；
- 访问密钥。

建议替换为：

- `疑似密钥已移除`
- `账号信息已移除`
- `内部地址已移除`

如果材料中检测到疑似密钥或账号密码，应优先移除，不应原样进入外部模型。

### 4.4 真实企业、客户和业务数据

应谨慎处理：

- 真实企业名称；
- 真实客户姓名；
- 真实订单编号；
- 真实业务报表；
- 真实金额、客户资料、业务数据；
- 未公开项目资料。

如教学确需引用，应泛化为：

- `某企业`
- `某客户`
- `示例订单`
- `示例业务数据`

AI 不得把未经教师确认的真实企业或真实数据写成正式案例。

---

## 五、可以保留的信息

以下内容通常可以保留：

- 课程名称；
- 知识点名称；
- 单元名称；
- 课题名称；
- 教学任务类型；
- 数据库技术术语；
- 示例数据库对象；
- 教学用表名、字段名；
- 专业名称的泛化表达；
- 年级或学习阶段的泛化表达。

示例：

- `MySQL数据库应用与管理` 可以保留；
- `GROUP BY`、`HAVING`、`SELECT` 可以保留；
- `student 表` 如果是教学示例表，可以保留；
- `中职二年级学生` 可以保留；
- `物联网专业学生` 可以保留；
- `23物联网2班` 不应保留，应替换为 `某班级`。

---

## 六、避免过度脱敏

脱敏不能破坏教学任务。

以下内容不应误删：

- SQL 中的示例表名，如 `student`、`score`、`course`；
- 示例字段名，如 `name`、`age`、`class_id`；
- 教学用示例数据；
- 课程术语中的“学生表”“教师表”；
- 泛化职业场景，如“客户信息表”“订单表”；
- 普通教学表述中的“学生”“教师”。

判断原则：

如果内容只是教学概念或示例对象，可以保留。  
如果内容能指向真实个人、真实班级、真实学校或真实组织，应脱敏。

---

## 七、替换策略

优先采用 Mask 方式，不直接阻断正常教学流程。

### 7.1 普通敏感信息

使用泛化替换：

- 学校 → `某校`
- 教师 → `某教师`
- 班级 → `某班级`
- 学生 → `某学生`
- 企业 → `某企业`

### 7.2 高风险安全信息

直接移除或替换：

- API Key → `疑似密钥已移除`
- 密码 → `密码信息已移除`
- Token → `疑似 Token 已移除`
- 内部地址 → `内部地址已移除`

### 7.3 无法确认的信息

如果系统无法判断内容是否真实，应优先采取谨慎策略：

- 对明显具备真实识别特征的信息进行泛化；
- 对教学必要内容保留；
- 在测试中覆盖误伤场景。

---

## 八、可配置规则

后续可增加机器可读配置文件，例如：

```text
config/ai_sanitization_rules.example.json
```

配置文件可用于定义：

- 敏感字段别名；
- 替换标签；
- 班级名称模式；
- 学校/部门关键词模式；
- 用户可扩展的正则规则；
- 允许保留的教学术语。

但核心安全流程不能完全依赖配置文件。

代码必须保证：

1. 输入真实 AI Provider 前一定调用脱敏；
2. AI 输出保存前一定调用脱敏；
3. API Key、Token、密码等高风险信息不会因配置错误而原样外发；
4. 测试覆盖关键脱敏规则。

## 九、建议配置示例

```
{
  "replacement_labels": {
    "school": "某校",
    "department": "某部门",
    "teacher": "某教师",
    "class": "某班级",
    "student": "某学生",
    "phone": "某手机号",
    "email": "某邮箱",
    "address": "某地址",
    "enterprise": "某企业",
    "secret": "疑似密钥已移除"
  },
  "class_name_patterns": [
    "\\d{2}(物联网|电子|电信|机器人|计算机|软件|网络|大数据)\\d班",
    "\\d{2}级?(物联网|电子|电信|机器人|计算机|软件|网络|大数据)\\d班"
  ],
  "allowed_teaching_terms": [
    "student 表",
    "score 表",
    "course 表",
    "学生表",
    "教师表",
    "客户表",
    "订单表",
    "中职学生",
    "物联网专业"
  ]
}
```

该配置仅作为示例。正式实现时应由代码提供默认安全规则，配置只作为扩展项。

## 十、日志与错误信息要求

日志、错误提示和测试输出中不得包含：

- 完整 API Key；
- 完整 Token；
- 密码；
- 教师上传的完整敏感原文；
- 未脱敏的学生、班级、学校信息。

允许记录：

- 是否触发脱敏；
- 触发的规则类型；
- 脱敏后的安全片段；
- 生成是否成功；
- 使用的 Provider；
- 使用的模型名；
- 非敏感错误类型。

------

## 十一、测试要求

至少应覆盖以下测试：

1. 输入 Prompt 前，真实班级名会被替换为 `某班级`；
2. 输入 Prompt 前，教师名会被替换为 `某教师`；
3. 输入 Prompt 前，学校名会被替换为 `某校`；
4. 手机号、邮箱、疑似身份证号会被替换；
5. API Key、Token、密码不会进入 Provider；
6. AI 输出中如果出现真实班级名，保存前会被替换；
7. 教学示例表名 `student`、`score` 不会被误删；
8. 普通课程术语“学生表”“教师表”不会被误删；
9. mock Provider 和真实 Provider 使用同一套脱敏入口；
10. 错误日志不包含未脱敏敏感信息。

------

## 十二、当前阶段建议

V0.2 阶段建议采取：

- 输入侧脱敏：必须实现；
- 输出侧脱敏：建议实现；
- JSON 配置：可先提供 example，正式可配置能力后续扩展；
- 高风险密钥检测：必须保留代码级兜底；
- 班级、学校、教师等行政信息：必须至少支持常见模式脱敏；
- 过度脱敏问题：通过测试逐步修正。
